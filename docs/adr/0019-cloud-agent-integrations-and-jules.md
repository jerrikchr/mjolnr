# ADR-0019: Cloud Agent Integrations and Google Jules Adapter

**Status:** Proposed
**Date:** 2026-08-21
**Deciders:** Jerrik Christiansen
**Related:** ADR-0003 (shared Rust core, clients), ADR-0006 (bounded workspace, trust classes), ADR-0008 (remote sync), ADR-0016 (capability modules vs plugin protocol), AGENTS.md §1 (prime directives), §3 (security), §8 (provenance), §11 (standing laws)

## Context

mjolnr orchestrates local agents (subagents, councils, worktree branches) and integrates bounded external task sources (GitHub, Linear, Vercel, Supabase). However, long-running, autonomous coding workflows are increasingly executed in ephemeral cloud VM environments by specialized remote agents—most notably **Google Jules** (powered by Gemini 3.6 Flash / Gemini 3 Pro).

Research into Google Jules (`jules-research`: `jules-sdk`, `jules-action`, `jules-skills`, and live UI flows) reveals an asynchronous cloud agent with distinct operational characteristics:
1. **Cloud VM Isolation**: Tasks run in Google's managed ephemeral VMs with pre-installed runtimes (Node.js, Python, Rust, Bun), operating directly on git branches.
2. **REST API & Activity Protocol** (`https://jules.googleapis.com/v1alpha`): Authenticated via `X-Goog-Api-Key`, exposing connected GitHub sources (`/sources`), sessions (`/sessions`), and streaming activities (`/sessions/{id}/activities`).
3. **Structured Artifacts**: Activities produce multi-step plans (`PlanStep`), unified git patches (`ChangeSet` / `gitPatch`), UI screenshots (`MediaArtifact`), and GitHub PRs (`PullRequest`).
4. **Governed Interaction Modes**: Supports review-first planning (pauses in `awaitingPlanApproval`), interactive requirement refinement, autonomous start, and scheduled skill-based maintenance tasks (security scans, performance audits, dependency updates).

### The Architectural Question

How should remote cloud agent runtimes (like Google Jules) be admitted into mjolnr?
* Are they read-only `TaskSource`s like Vercel and Supabase? (No: Jules actively writes code, generates diffs, and opens PRs).
* Are they local JSON-RPC subprocess plugins under ADR-0016? (No: Jules runs remotely in Google's cloud infrastructure, requires account-level API authentication, and streams rich activity feeds).
* Are they full agent loop replacements? (No: mjolnr's prime directive states *the model proposes, mjolnr's deterministic code disposes*).

## Decision

**Establish `CloudAgent` as a first-class integration category in mjolnr, implemented as first-party Rust modules in the core, with Google Jules as the reference cloud agent adapter.**

### 1. The Taxonomy: Modules, Plugins, MCP, and Cloud Agents

| Category | Execution Environment | mjolnr Boundary | Examples |
|---|---|---|---|
| **Capability Module** | In-process first-party Rust | Single crate, authoritative state | `src/memory/`, `src/runtime/`, `src/providers/` |
| **Task Source** | Remote REST API (read-only context) | `src/integrations/` | GitHub Issues, Linear, Vercel deployments, Supabase |
| **Plugin** | Local subprocess JSON-RPC (stdio) | `mjolnr-plugin.yaml`, observer hooks | Community extensions, custom inspectors |
| **MCP Server** | Local or remote stdio/HTTP tools | `ToolTier::Execute` policy gate | Neon, Tinybird, Context7, v0, Postgres |
| **Cloud Agent** | Remote ephemeral cloud VM | `src/integrations/jules/` (REST wire) | **Google Jules**, (future: Copilot Workspace, Devin) |

### 2. The Google Jules Adapter (`src/integrations/jules/`)

mjolnr implements a native Rust client talking directly to `https://jules.googleapis.com/v1alpha` without importing the Node SDK (satisfying AGENTS.md §8 "No unofficial provider SDKs. Adapters are written against documented REST contracts").

The adapter manages:
1. **Credentials**: `JULES_API_KEY` stored in mjolnr's owner-only credential file store (`SecretStore` in `src/store/secrets.rs`), with browser-based account connection in the onboarding/auth UI.
2. **Source Resolution**: Mapping the local git workspace (`remote.origin.url`) to Jules connected sources (`sources/github/owner/repo`).
3. **Session Dispatch**: Creating cloud tasks with prompt, starting branch, automation mode (`AUTO_CREATE_PR` or `AUTOMATION_MODE_UNSPECIFIED`), and plan approval requirements (`requirePlanApproval`).
4. **Activity Streaming & Hydration**: Consuming paginated, time-filtered activity events (`planGenerated`, `agentMessaged`, `progressUpdated`, `sessionCompleted`, `sessionFailed`) with incremental local caching.
5. **Plan Approval**: Forwarding human approval decisions (`POST /sessions/{id}:approvePlan`) when sessions enter `awaitingPlanApproval`.
6. **Artifact Ingestion**: Extracting unified diffs (`ChangeSet`), screenshots (`media`), and PR links (`pullRequest`).

### 3. Provenance, Governance, and Trust (Standing Law & Prime Directives)

* **External Provenance (`TrustClass::ExternalUnverified`)**: All code generated by Jules arrives with external unverified trust. It does not bypass mjolnr's gates.
* **Deterministic Local Verification Gate**: When a Jules task finishes (or a patch is fetched), mjolnr imports the `gitPatch` or branch into an isolated local worktree (`mjolnr/jules-<id>`). Before merging to the main working tree, mjolnr executes the project's deterministic test suite (`cargo test`, `npm test`, linter) locally.
* **Never Lie About State**: Jules PRs and cloud tasks are marked as "Cloud Agent - External Unverified" until local verification proves passing status.
* **Secret Boundary**: Provider API keys (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, etc.) are never transmitted to Jules. Jules operates strictly with the user's `JULES_API_KEY` and Google Cloud VM credentials.

### 4. Client Projections (Desktop SvelteKit & TUI)

1. **Fleet Rail Projection**: Active Jules sessions appear on mjolnr's Fleet / Glassbox surface alongside local subagents, displaying status (`queued`, `planning`, `awaitingPlanApproval`, `inProgress`, `completed`, `failed`), step indicators, and duration.
2. **Interactive Plan Review Surface**: When Jules pauses in `awaitingPlanApproval`, the Desktop UI and TUI render the multi-step plan with a 1-click **Approve Plan** action.
3. **Diff & Media Artifact Viewer**: Renders generated diffs and test screenshots in mjolnr's native inspector.
4. **Scheduled Cloud Skills**: mjolnr exposes reusable cloud skill templates (Security Sentinel, Performance Optimizer, Weekly Cleanup, CI Failure Fixer) derived from curated prompt specs.

## Consequences

### Positive
- Allows mjolnr users to offload heavy, asynchronous, or long-running tasks to Google's cloud VMs while maintaining local governance and verification.
- Establishes an extensible `CloudAgent` contract for future remote coding platforms.
- Complete architectural isolation: clean REST API boundary, zero foreign runtime dependencies in the Rust core.

### Accepted Costs
- Polling and rate-limit management over `jules.googleapis.com` (handled via exponential backoff and incremental timestamp filtering).
- Dual-state management: synchronizing remote cloud session states with local SQLite session mirrors.

## Verification & Architecture Rules
- Bounded network calls: all Jules REST requests enforce timeouts, max response body limits, and time-based backoff.
- Architecture test (`tests/architecture.rs`) enforces that `src/integrations/jules/` depends only on `core` and `providers`/`integrations` shared network primitives, never on clients (`tui`, `desktop`).
